# WordWebCMS 现代化改造与未完成功能评估

评估及修订日期：2026-10-28。实施状态：已按已确认的设计完成 A～D 阶段首版实现；构建、真实 MySQL 流程、浏览器及备份恢复验证见 [实施与验收记录](Modernization-Implementation.md)。第 1～3 节保留改造前源码评估，第 4～6 节描述方案与范围；下文旧版路径和构建错误是改造前的历史记录。完成复核后已删除旧源码目录，发布方式按最新要求调整为标准目录发布。

## 1. 改造前结论与核查范围（历史记录）

改造前项目具备博客前台原型，但尚未形成可日常使用的 CMS。当时最重要的缺口是后台内容管理闭环，以及迁移到 ASP.NET Core 的可运行基础；这些首版缺口现已完成。

新版定位为“轻量、可自行部署、支持多人投稿审核、公众注册评论、Markdown 与原生主题的 C# CMS”。采用 .NET 10、ASP.NET Core Razor Pages、MySQL 与 FreeSql。全新安装并重新设计表结构，不迁移旧密码、旧表结构、旧 API 或旧地址；共享账号库，但各站角色隔离。原生主题同时支持随程序发布和后台上传，不做 WordPress 格式兼容。

首版覆盖文章与页面、独立未发布修改和修订、单分类与标签、媒体、账号与站点权限、评论审核、计算点赞量、站点设置及原生主题。有发布权限者直接发布，无发布权限者提交审核；不纳入定时发布、等级、经验、金钱或完整插件平台。按标准目录方式发布。

原始评估依据当时工作区源码、页面、SQL、项目配置及调用关系。评估时没有连接数据库、发送邮件、运行安装程序或访问部署站点；旧版业务仅确认有源码路径，不代表运行验收通过。未检查远端历史分支或外部项目看板，下列“未发现”限于当时工作区。

- `WordWebCMS.old/WordWebCMS.old.csproj:15`：旧版目标是 .NET Framework 4.6.2，使用 Web Forms、MySQL、LinePutScript.SQLHelper 和 Westwind Markdown。
- `WordWebCMS/WordWebCMS.csproj:4`：新版目标为 .NET 6。
- `WordWebCMS/Program.cs:10`：新版仅注册返回 `Hello World!` 的首页，没有 CMS 路由、认证、数据库或页面注册。
- 新版仍保留 `Index.aspx.cs`、`Login.aspx.cs`、`Function/Function.cs` 等旧文件，SDK 默认把这些 C# 文件纳入编译。
- 工作区在本次分析之前已有大量迁移改动，旧目录为未跟踪状态；本次不改动这些文件，不删除、提交或回滚用户工作。

构建核查：执行 `dotnet build WordWebCMS/WordWebCMS.csproj --no-restore --nologo -v:q`，得到 **8 个错误、1 个警告**。错误涉及 `System.Web.UI`、`Page`、`LinePutScript`；警告为 .NET 6 已不受支持。这不是补一个 using 就能解决的依赖问题：ASP.NET Core 不支持 Web Forms 页面运行模型。旧项目未构建，未创建测试工程。

截至评估日期，建议直接选 .NET 10 LTS，官方支持表列出支持至 2028 年 11 月；.NET 8/9 已接近 2026 年 11 月的支持终点。参考 [Microsoft 支持策略](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) 与 [框架选择说明](https://learn.microsoft.com/en-us/dotnet/standard/choosing-core-framework-server)。

## 3. 改造前发现的具体问题（历史记录）

### 3.1 迁移和发布前必须处理

1. **新版无法编译，业务入口尚未迁移。** `Program.cs` 仅有示例路由；Web Forms 残留不能直接运行在 ASP.NET Core。先整理新旧编译边界，再逐条实现页面流程，不为旧 Page/Session/Application 编写模拟框架。
2. **登出只有提示，没有失效动作。** `WordWebCMS.old/Login.aspx.cs:145-148` 仅显示面板，没有清除 `Session["User"]`。Release 下 `Page_Load:18-23` 还会先把已登录用户重定向到用户页，阻断登出分支。应以框架登录/登出流程取代。
3. **评论写入缺少目标校验和授权。** `AJAX.ashx.cs:141-175` 检查登录和非空文本后直接插入；没有读取目标文章、核对文章可见性、`AllowComments` 或封禁角色。`Post.aspx.cs:119` 隐藏输入区不能替代写入接口检查。
4. **旧密码算法不应迁移。** `Function/Function.cs:24-37` 使用 `GetHashCode()` 拼接后 MD5，既不是合适的密码哈希方案，也不能依赖跨运行环境一致性。Microsoft 明确不保证字符串哈希跨运行环境稳定，见 [GetHashCode 文档](https://learn.microsoft.com/en-us/dotnet/api/system.string.gethashcode?view=net-10.0)。已决定全新安装，重新设计账号表并使用成熟密码哈希组件，不迁移旧密码，也不实现旧哈希验证或兼容回退。
5. **找回密码未形成可靠令牌生命周期。** `Login.aspx.cs:108-142,409-413` 用普通 Random 和 Application 保存状态，打开链接便生成密码，密码还保存在应用内存供重复显示。应改成有有效期、单次消费的重置凭证，由用户提交新密码。注册验证码在 `AJAX.ashx.cs:128` 和 `Login.aspx.cs:304-325` 之间也未见绑定已验证目标邮箱。
6. **安装写入未全部参数化，入口锁定不完整。** `Setup.aspx.cs:234` 把管理员名和邮箱直接插入 SQL；`Page_Load:20-41` 的 return 只退出页面加载方法，写操作事件处理器没有共同核对安装是否已锁定。新实现应在每个安装写入口执行同一实际授权规则，安装完成后锁定，禁止沿用已知默认管理员密码。
7. **内容输出边界不统一。** `Posts.cs:580-597`、`Review.cs:431-437`、`Master.cs:21` 直接拼接标题、作者、摘要、URL 等进入 HTML；创建和更新路径的清洗行为也不一致。`Posts.cs:470` 传 `!AnalyzeHtml`，而评论传 `AnalyzeHtml`，语义相反。新版已确定：评论全部禁止原始 HTML，文章统一采用允许列表；普通文本由模板编码，Markdown 生成的 HTML 按统一规则处理，不设置管理员绕过。旧代码风险未做浏览器攻击验证，不描述成已复现漏洞。
8. **写操作的 HTTP 边界不完整。** 点赞和发验证码使用 GET，AJAX 写入口未见抗伪造验证；新站采用明确的 POST、服务端授权和框架表单防伪造机制。这是公开 Web 输入边界，不属于技能中要删除的内部无意义防御代码。

## 4. 按已确认方向调整的现代化结构

### 4.1 一个 Web 项目，少量具体服务

采用 .NET 10 + ASP.NET Core Razor Pages + MySQL + FreeSql。Razor Pages 承担页面路由、管理后台及表单交互；前台外观由原生主题模板控制。页面表单逻辑可以直接放在 PageModel，符合用户偏好的直接、易修改代码，见 [官方说明](https://learn.microsoft.com/en-us/aspnet/core/razor-pages/?view=aspnetcore-10.0)。保持一个 Web 项目，不另建 SPA、独立 API 或多个部署单元。

建议按实际出现的功能逐步形成下面的结构，不预先生成空目录和空服务：

```text
WordWebCMS/
  Program.cs
  Pages/                 # 首页、文章、归档、搜索、账号
    Admin/               # 文章、页面、评论、媒体、用户、设置
    Shared/              # Layout 与公共局部模板
  Models/                # Post、Comment、Category 等普通 class
  Services/              # 实际复用的文章保存、评论处理、设置、媒体操作
  Data/                  # FreeSql 配置、实体映射及新版建表/升级入口
  theme/                 # 随程序发布和后台上传的原生主题
    default/             # 默认主题的清单、模板与静态资源
  wwwroot/               # 固定版本的公共脚本、样式
```

PageModel 处理输入、响应和页面交互；跨页面复用的发布、审核等操作放具体服务。没有第二个实现时不自动添加接口、工厂、GenericRepository、UnitOfWork、事件总线或 CQRS。框架要求的入口和业务含义清晰的方法应保留，不机械内联。

数据访问统一使用 FreeSql，MySQL 驱动采用 `FreeSql.Provider.MySqlConnector`。这是 FreeSql 官方列出的 Provider，参见 [FreeSql 入门文档](https://freesql.net/en/guide/)。不再把直接 MySqlConnector SQL 或 EF Core 作为并列方案，也不为了使用 ORM 再包装一层自定义通用仓储。普通实体 class 保存数据，实际服务显式查询和保存；分页、关联查询、聚合计数及必要事务直接使用 FreeSql。

共享账号库和当前站点内容库各自拥有明确的 FreeSql 访问对象；同一数据库配置的 `IFreeSql` 实例按应用生命周期复用，事务仅限实际操作范围。保留这两个入口是因为有真实的数据库职责差异，不扩展成任意数据库路由器。

全新表结构从实体设计开始，首次安装显式调用 CodeFirst 建表；MySQL 数据库本身由部署环境预先创建。生产环境不依赖业务请求触发自动改表，新版本升级走明确的执行入口及版本记录。FreeSql 的 CodeFirst 支持结构同步，但不等同于完整、自动的数据迁移，参见 [CodeFirst 文档](https://freesql.net/en/guide/code-first.html)。不生成旧版升级脚本，不沿用旧 `setup.sql` 或旧字段。

### 4.2 数据模型只支持已经确定的业务

- **文章与页面**：建议共用 Post 表和编辑器，用简单类型字段区分。线上发布版本与编辑工作版本分开保存；可见性、置顶顺序和实际发布时间单独表达，不把置顶混入发布状态。
- **草稿与修订**：已确认支持独立未发布修改和修订。建议用 Post 的 `PublishedRevisionId` 指向线上版本，`PostDraft` 保存当前编辑内容，`PostRevision` 保存提交或发布时的版本。前台只读线上版本，保存草稿不修改线上内容；这些记录是必要业务数据，不属于防御性 Clone。
- **直接发布与审核发布**：有发布权限者可发布当前修改；无发布权限者提交一个明确修订版本供审核。审核期间继续编辑不改变已提交版本，审核通过只发布被审核的版本。修订、分类/标签关系与线上版本切换在同一站点库事务内完成，不设置定时发布状态或调度任务。
- **单分类与标签**：每篇文章只对应一个分类，可关联多个标签。采用 Category、Tag、标签关联记录；分类与标签选择属于可修订的文章内容，草稿修改不能提前影响线上归档。具体映射随版本模型落实，不再使用拼接字符串分类或文章多分类关联。
- **评论**：公众注册登录后可评论，保留 Markdown 与回复关系；全部禁止原始 HTML。回复使用 ParentId，评论审核与文章发布权限分开执行，不再把引用协议塞进正文。
- **媒体**：记录文件路径、名称、类型、大小、替代文本和上传者；先支持本地持久目录。数据库与文件的备份恢复要配套。
- **账号与角色**：共享账号库保存 User、密码哈希、邮箱验证及重置凭证；当前站点库保存 SiteUserRole，以共享 UserId 关联。普通实体和显式角色字段即可，不做动态权限引擎。各站创建自己的管理员，不继承旧 `isroot` 跨站管理员语义。共享账号库不等于自动跨域登录或共享登录 Cookie。
- **点赞量**：本方案将“计算点赞量”落实为对点赞记录做 COUNT/分组聚合。文章和评论各自保存用户点赞记录，并对目标 ID + UserId 建唯一约束；列表页批量统计当前页目标，不逐条查询，也不额外持久化 Likes 总数。用户点赞状态来自同一记录源，重启后仍有效。
- **移除社区数值**：新用户模型不包含 money、exp、lv 等金钱、经验、等级字段，也不建立对应服务或兼容属性；已有文章阅读量与这些社区数值分开处理。
- **设置与导航**：小型站点可以保留简单键值设置；导航条目需要排序和父子关系时再建立明确结构，不先做通用内容元数据引擎。

上述表名及版本指针是对已确认需求的实现建议，落地时保持最少实体与明确所有权。新版本自身的数据库升级仍是维护需求；旧版数据兼容已明确放弃，不加入旧字段探测、旧 API 转发、旧密码回退、旧 URL 跳转或旧 LPS 格式兼容。全新安装意味着使用新数据库结构，不代表本次可以删除现有数据库或旧源码。

### 4.3 账号与内容边界

首版已确定包含多人投稿审核及公众注册评论，不再保留“仅站长账号”的产品分支。认证建议采用 ASP.NET Core Cookie 与框架密码哈希组件，账户、邮箱验证和重置凭证通过 FreeSql 保存。Cookie 仅负责登录票据，注册验证、凭证到期与单次消费、密码重置及账号禁用后的票据失效仍须形成完整流程，见 [Cookie 认证说明](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0)。复用框架加密和认证能力，不重新发明密码算法，也不默认引入 EF Core 或一套可切换认证框架。具体账号组件接入属于实施细化，不改变 FreeSql 与角色隔离的既定方向。

建议最小角色为注册用户、投稿者、编辑、管理员：注册用户可评论；投稿者可写自己的内容并提交审核；具备发布权限的编辑/管理员可直接发布及审核。注册是否自动取得投稿资格尚未由“公众注册评论”指定，暂建议由站点管理员授予投稿权限，作为下文保留的产品细节。所有角色只在当前站点生效，读写入口都执行规则，不仅隐藏按钮。

评论输入禁用原始 HTML；Markdown 生成的链接、图片等输出也校验允许的 URL 协议。文章经 Markdown 渲染后统一按标签、属性和 URL 协议允许列表处理，预览和公开展示共用规则，管理员文章也无绕过开关。普通标题、摘要和用户名由模板编码。外部输入验证、上传限制、参数化查询和表单防伪造对应实际 Web 入口，属于必要边界。

### 4.4 主题与编辑体验

先做一个完整、响应式的默认主题：前台文章、列表、页面、归档、搜索、评论、错误页，以及单独稳定的管理后台。把 `Posts.ToIndex/ToPost`、`Review.ToPostReview`、`Users.ToWidget` 中的 HTML 搬到模板，数据对象不再决定页面结构。

已确认同时支持随程序发布的默认模板和后台上传的原生主题，统一放在 `theme/<主题标识>/` 下。每个主题包含清单、前台模板和静态资源，后台提供上传、列表及启用入口；管理后台保持自身布局，不随前台主题改变。主题安装要检查包内路径和必需文件，避免覆盖主题目录外的程序与配置；模板文件不作为静态资源直接公开。

前台主题需使用运行时可读取的原生模板机制，使上传后启用不依赖站点源码重编译或在运行环境安装 SDK；普通编译期 Razor 模板本身不能满足这一点。模板引擎的具体包和语法在实施时选择，默认主题和上传主题共用同一约定，不自行编写通用解释器，也不引入任意 C# / DLL 插件执行。主题只读取准备好的页面数据，不直接访问数据库。

已明确放弃 WordPress 兼容。旧 README 中的 CSS 兼容描述属于历史说明，新版交付文档应改为 WordWebCMS 原生主题，不实现 WordPress PHP 模板、区块格式、插件 API 或旧 WWC 占位符兼容层。

写作首版保留 Markdown，增加预览、封面、摘要、分类、slug、草稿/发布动作。自动保存只在编辑内容变化后触发；修订记录按明确保存时机生成。不要为了追求区块编辑器而先构建页面搭建引擎。

### 4.5 标准发布与持久化

使用标准 `dotnet publish -c Release` 产物部署，在开发机使用 SDK 构建，部署环境安装 .NET 10 ASP.NET Core 运行时即可。

数据库地址通过部署配置或环境变量提供；上传文件、用户安装的主题及认证密钥放在独立可写持久目录，替换程序时保留。首次部署要把随程序提供的默认主题初始化到有效主题目录；后续部署保留用户安装的主题。按 Linux 大小写规则验证模板和资源路径，不依赖 IIS 专有重写或 Windows 专有 API。暂不引入集群、自动部署平台或多存储 Provider。

## 7. 按实用主义技能落实的改造边界

值得保留的是 Markdown 内容形式、文章/评论业务语义、已有视觉素材，以及共享账号但角色隔离的产品目标。需要替换的是 Web Forms 页面生命周期、旧数据库结构、旧密码算法、隐藏数据库 IO 的属性、HTML 拼接和多份 Application 缓存。FreeSql 直接承载新模型的读写，不为旧实现建立适配层。

先删无调用的残留与过时迁移代码，再消除重复状态和复制出来的设置逻辑，然后补齐真正的用户操作。每步围绕一个可验收流程推进，不先大规模改名、分程序集、引入微服务、缓存服务器或通用插件框架。

评估阶段仅修订文档。随后的实施已修改新版业务代码、安装依赖并操作隔离/用户指定测试库，具体范围与验收证据以 [实施与验收记录](Modernization-Implementation.md) 为准；没有部署生产站点。
